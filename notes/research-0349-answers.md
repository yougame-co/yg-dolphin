## A. Ticket and room identity

### A1. Ticket parsing versus room identity

**The match ticket string is opaque to the inspected client paths.** Initial acquisition reads the reply's `url` and `ticket`, checks nonemptiness and the room URL, caches the ticket, and separately reads reply metadata `keyframes`, `ice`, `direct`, and `tourney`. Refresh reads/caches another ticket string. Connection puts the escaped whole string in `?ticket=`. There is no payload/base64/signature/`u`/`p` interpretation in these functions (`YouGameRoom.cpp:1690-1707`, `YouGameRoom.cpp:1799-1835`, `YouGameRoom.cpp:2362-2384`). The watch-ticket path likewise reads `url`, `ticket`, and `watch` from the response and constructs the watch URL (`ReplayStream.cpp:680-732`). The **reply envelope and metadata must remain usable** even if the ticket's internal account fields change (`YouGameRoom.cpp:1603-1615`, `YouGameRoom.cpp:1690-1707`).

### A2. Roster `user` / account IDs

**No semantic read of roster `user` or an account ID was found in the requested client flow.** The participant parser selects `slot`, `id`, and `connectionId`; the roster selects `connectionId`, `slot`, and `name`; away/recovery reads `away` and connection identity. ### A3. Authentication assumptions, bounds, and server comparison

**Client request and transport contract.** The ticket request supplies lobby `{version:1,minPlayers:2,maxLocalPlayers:1,compatibility}`, player count `MAX_SEATS`, mode and room; the app-bridge request adds `type:mpTicket` and `ranked:false`. The dev-only path supplies its chosen `player_id` and display name. Refresh repeats the same room/lobby contract (`YouGameRoom.cpp:1522-1526`, `YouGameRoom.cpp:1653-1684`, `YouGameRoom.cpp:1747-1787`). Room codes are 6–12 lowercase ASCII letters/digits. Room URLs must be HTTPS/WSS except explicit localhost/127.0.0.1 test origins (`YouGameRoom.cpp:115-119`, `YouGameRoom.cpp:790-804`).

**Client ticket contents and signatures.** The client requires a nonempty ticket string, not particular claim fields, signature length, signature algorithm, or a particular number of dot-separated components. It forwards the string to the room and to the replay store (`YouGameRoom.cpp:1690-1706`, `YouGameRoom.cpp:1822-1835`, `YouGameRoom.cpp:2371-2374`, `Keyframe.cpp:1137-1143`). The stdio envelope has 64 KiB maximum inbound lines and the generic stdin splitter 128 KiB; outbound bridge requests are bounded at 32 KiB (`Bridge.h:36-43`, `Source/Core/DolphinNoGUI/Embed.cpp:208-232`). These are envelope limits, not a client 4096-character ticket limit. The actual bridge parser uses `MAX_INBOUND` (`Source/Core/Core/Orca/Bridge.cpp:197-204`). End-to-end HTTP/edge/WebSocket-upgrade URL/header size limits and the server's actual signing/verifying algorithm are **UNKNOWN** from the two server helpers and these ticket call sites.

**Lifetime and retry.** The client caches a ticket until refused for a transfer, with no local expiry-claim parsing. The server helper documents a five-minute room ticket and explicitly defines six hours of replay-store grace. These agree at the helper/assumption level; actual signature/grace verification is **UNKNOWN** because the verifier is not in either compared server file. Transfers refresh on `401/ticket` or `403/signed_out` and stop on other terminal 4xx codes; 429/5xx/network failures retry (`YouGameRoom.cpp:1719-1744`, `Keyframe.cpp:1260-1279`, `keyframes.ts:28-33`, `keyframes.ts:105-125`).

### Verdict for 0.3.48

**Inference: no client break is demonstrated solely by `u:null`, a stable opaque participant/seat ID, `user:null` in the public view, and an encrypted server-only account-list field.** The client passes the ticket untouched, parses no roster account field, and uses strings as identity keys (`YouGameRoom.cpp:1690-1706`, `YouGameRoom.cpp:3007-3019`, `YouGameRoom.cpp:3044-3080`, `YouGameRoom.cpp:4033-4059`). This is conditional on preserving the existing response, numeric-seat, connection, policy-envelope, and stable-match-ID contracts described above; it is not a verdict on an uninspected server implementation.

Concrete breaks or conditions to avoid:

1. **Unchanged server transfer authorization:** ranked `u:null` is refused; arbitrary aliases fail the casual guest predicate and can fail bound private guests. A legacy private alias that passes is instead treated as a guest, changing ownership/seating semantics (`keyframes.ts:132-161`, `keyframes.ts:225-237`). The client needs replay transfer for drop-in and treats `signed_out` as a refreshable refusal, then reports refusal if still denied (`OnlineMatch.cpp:1435-1458`, `Keyframe.cpp:1260-1279`).
2. **Ticket encoding/size or policy-envelope change:** more than 4096 allowed characters, an incompatible alphabet, encrypted outer JSON, or hidden `ot`/`l` breaks the corresponding server helper. These are server constraints, not client account decoding (`keyframes.ts:61-74`, `orca-online-policy.ts:137-164`).
3. **Connection alias rotation during rejoin:** changing welcome `me` or the numeric slot ends recovery; changing peer connection IDs also changes peer/direct-link identity. An alias must remain stable across the held-seat recovery (`YouGameRoom.cpp:4151-4162`, `YouGameRoom.cpp:4248-4267`, `YouGameRoom.cpp:4033-4059`, `Source/Core/Core/Orca/Session/DirectLink.cpp:1398-1401`).
4. **Inconsistent or rotating participant aliases within a match/set:** `start` snapshots participants; reports and verdicts must use those same IDs. If “per-game” means a new alias for every fight of one ranked set, consistency with that snapshot is required; otherwise winners/scores can be attributed incorrectly. Changing only prefix/shape is safe at these sites; empty IDs, IDs over 128 bytes, or replacing numeric `slot` with a string are not (`YouGameRoom.cpp:3007-3019`, `YouGameRoom.cpp:3578-3586`, `YouGameRoom.cpp:3154-3169`, `YouGameRoom.cpp:3393-3429`).
5. **Server account lists must still resolve internally:** encrypted IDs cannot simply replace the account inputs to current ownership/test-room functions. Public-view masking is separate from server DB identity; actual decrypt/verification/matchmaking integration and desktop mirror consumers remain **UNKNOWN** (`keyframes.ts:159-161`, `keyframes.ts:225-237`, `orca-online-policy.ts:177-195`, `YouGameRoom.cpp:2705-2715`).

## B. Theater mode

### B1. Live resize and minimum size

**Live resizing is implemented; no restart is requested in the resize path.** macOS's window delegate calls `ResizeSurface`; embed `rect` updates geometry and layout, then tracks the parent window. The macOS frame is set without animation, and embedded event polling is 120 Hz (`PlatformMacos.mm:134-140`, `Platform.cpp:269-292`, `PlatformMacos.mm:518-525`, `PlatformMacos.mm:581-595`). Win32 `WM_SIZE` and X11 configure events also notify the presenter (`PlatformWin32.cpp:386-390`, `PlatformX11.cpp:550-553`).

The presenter flags the resize under a mutex. Metal observes it on backbuffer bind, updates drawable size/backbuffer wrappers, and informs the presenter; draw rectangles are recalculated. Aspect fitting centers the image and preserves bars unless a stretch/crop mode says otherwise. Embed layout hints deliberately retain the previous applicable layout while the new surface catches up (`Present.cpp:720-724`, `MTLGfx.mm:639-649`, `MTLGfx.mm:694-726`, `Present.cpp:392-420`, `Present.cpp:677-685`, `Present.cpp:831-846`, `Present.cpp:881-949`).

**Internal resolution is separate from box dimensions.** Config defaults to 1x; fixed scale stays fixed on window resize. Auto integral scale (`0`) can recreate EFB/readback buffers when a size change crosses a scale threshold; that path destroys and creates buffers. A live `gfx res` command can also change scale (`Source/Core/Core/Config/GraphicsSettings.cpp:91-92`, `VideoConfig.h:20`, `Present.cpp:411-421`, `FramebufferManager.cpp:93-101`, `FramebufferManager.cpp:213-225`, `Perf.cpp:277-284`, `Perf.cpp:358-364`). **Inference:** fixed internal scale avoids that particular resize-driven recreation cost. Exact latency, smoothness, black flashes, dropped frames, and sustained resize performance are **UNKNOWN** without running; the code permits skipped presentation when Metal has no drawable (`MTLGfx.mm:588-604`, `MTLGfx.mm:645-648`).

**Embedding has a 32-pixel minimum side.** A rect below 32 in either dimension hides the game at its last size; startup clamps to at least 32 and starts hidden until a sufficiently large rect arrives. That is a rendering guard, not a usable UX minimum (`Embed.h:47-54`, `Embed.cpp:154-156`, `Platform.cpp:275-292`). On macOS the supplied rect is in physical pixels, converted using screen backing scale (`PlatformMacos.mm:497-525`). No application content minimum is set in the standalone macOS creation code; any OS-imposed standalone minimum is **UNKNOWN** (`PlatformMacos.mm:234-244`). The overlay has a different 100-pixel picture-height cutoff (B5).

### B2. Default aspect and host controls

**Default presentation is Auto, with crop off; Orca sessions set Wii widescreen true.** Wii Auto consults `SYSCONF_WIDESCREEN` (subject to explicit suggested/forced aspect settings), so the normal unoverridden session is approximately 16:9. The calculation uses VI aspect rather than assuming an exact texture ratio; ForceStandard uses the source/approximately 4:3 aspect, ForceWide expands to approximately 16:9, and Stretch fits the layout box (`Source/Core/Core/Config/GraphicsSettings.cpp:22-28`, `Source/Core/Core/Config/GraphicsSettings.cpp:37`, `Profile.cpp:149-154`, `Widescreen.cpp:56-80`, `Present.cpp:535-584`, `VideoConfig.h:22-30`). Resizing an Auto box does not itself select Stretch; it fits/centers the picture with letterboxing/pillarboxing (`Present.cpp:881-949`). Effective settings in a user's installation or an arbitrary mod are **UNKNOWN** here.

**The host can choose an aspect at startup using the existing generic config flag.** `--config` accepts `<System>.<Section>.<Key>=<Value>`; `GFX.Settings.AspectRatio` names the aspect setting and the enum maps Auto=0, ForceWide=1, ForceStandard=2, Stretch=3. Thus startup arguments can request the presentation mode, subject to higher effective configuration overrides (`Source/Core/UICommon/CommandLineParse.cpp:46-60`, `Source/Core/UICommon/CommandLineParse.cpp:99-103`, `Source/Core/Core/Config/GraphicsSettings.cpp:22`, `VideoConfig.h:22-30`, `MainNoGUI.cpp:398-422`). No dedicated live aspect command appears in the embed dispatcher; the live `gfx` whitelist includes resolution/filtering/etc., not aspect. `view` controls the layout box/cropping relationship, not the aspect enum (`Platform.cpp:295-320`, `Platform.cpp:418-427`, `Perf.cpp:277-285`). A live host aspect command would need a new dispatcher/setting update; visual results of forcing 4:3 on the widescreen game's UX are **UNKNOWN** without validation (layout assumptions in B5).

### B3. Keyboard, pads, focus, and clicking away

**Embedded focus belongs to the host.** On macOS the render window cannot become key/main and ignores mouse events. Input focus is true only when the parent is onscreen, the host's last command grants focus, and its owning app is frontmost. Win32 and X11 use corresponding host-foreground/focus conditions (`PlatformMacos.mm:117-126`, `PlatformMacos.mm:366-371`, `PlatformMacos.mm:560-565`, `PlatformWin32.cpp:337-348`, `PlatformX11.cpp:376-400`). Clicking chat inside the same host app therefore requires the host to send `blur`; simply staying in that app does not revoke the previous grant. `focus`/`blur` are already accepted commands (`Platform.cpp:360-365`, `PlatformMacos.mm:560-565`).

**Keyboard capture and game input are distinct.** The native Quartz keyboard implementation reads HID system key state, rather than only window key events. However, macOS Orca sessions using the stdio bridge disable the native keyboard entirely because the page supplies it as a pad. Outside that case native inputs still pass through the input gate (`Source/Core/InputCommon/ControllerInterface/Quartz/QuartzKeyboardAndMouse.mm:192-195`, `Sandbox.cpp:245-248`, `MainNoGUI.cpp:607-618`, `Source/Core/InputCommon/ControlReference/ControlReference.cpp:88-92`). The code alone does not prove that the host page correctly cancels every key on blur; that host behavior is **UNKNOWN**.

**Background Input defaults false and embedding explicitly forces false for that run.** Standalone can retain a user's setting; the universal session settings inspected do not force it there. Each SI poll updates the gate from Background Input and renderer focus. When the gate is false, mapped input references return zero, and the app controller source explicitly returns a neutral pad, covering both app gamepad/adapter choices (`Source/Core/Core/Config/MainSettings.cpp:532`, `MainNoGUI.cpp:607-610`, `Source/Core/Core/HW/VideoInterface.cpp:949-958`, `Source/Core/Core/Core.cpp:1051-1060`, `Source/Core/InputCommon/ControlReference/ControlReference.cpp:88-92`, `ControllerSource.cpp:681-695`). GCPad builds a fresh pad with buttons/sticks/triggers from those references; it does not keep the previous whole mapped pad on blur (`Source/Core/Core/HW/GCPadEmu.cpp:137-177`).

**For the online path, clicking away sends neutral input while the match continues, once focus loss reaches the gate.** Rollback samples app `LocalPad` or Dolphin's mapped port 1 and encodes that result, with the gate also passed to the UX input filter. Pause-on-focus-loss is forced off, and `blur` only changes focus (`Source/Core/Core/Rollback/Rollback.cpp:618-642`, `ControllerSource.cpp:692-695`, `Profile.cpp:100-101`, `Platform.cpp:360-365`). It is not an indefinitely held last local pad. A missing remote packet is different: session prediction repeats the last known input until corrected, and excessive lead stalls (`Source/Core/Core/Orca/Session/Session.cpp:1444-1453`, `Source/Core/Core/Orca/Session/Session.cpp:895-909`). Input-gate update latency and a host failing to send blur are **UNKNOWN** runtime/integration details. The low-level native `GCAdapter::Input` itself returns cached adapter status without this focus check, so the neutral-pad conclusion is scoped to the actual Orca app/mapped online route, not every upstream Dolphin adapter API (`Source/Core/InputCommon/GCAdapter.cpp:847-871`, `Source/Core/Core/Rollback/Rollback.cpp:635-642`).

### B4. Focus, occlusion, resize, netplay, and throttling

**Inference: focus loss itself is an input change, not a demonstrated desync/stall trigger.** It does not pause the session and returns ordinary neutral input through the regular online sampling path. Resize changes the host surface/layout, not the room identity or pad protocol (`Profile.cpp:100-101`, `ControllerSource.cpp:692-695`, `Source/Core/Core/Rollback/Rollback.cpp:634-642`, `Platform.cpp:269-292`, `Present.cpp:720-724`). This is not a guarantee that arbitrary GPU/OS delays cannot stall the match; the session stops advancing when its confirmed-frame gap exceeds its stall limit (`Source/Core/Core/Orca/Session/Session.cpp:895-909`). A true desync is detected by unequal checksums at the same frame; a display delay is not itself evidence of unequal emulated state (`Source/Core/Core/Orca/Session/Session.cpp:1787-1800`).

Existing macOS protections are substantial:

- **App Nap:** bundle plist sets `NSAppSleepDisabled=true` (`Orca-Info.plist.in:34-38`). Whether an installed/non-bundled executable has that plist and how the OS schedules it is **UNKNOWN**.
- **Occlusion:** observes `NSWindowDidChangeOcclusionStateNotification`; combines occlusion state with embed visibility and reports surface visibility to the presenter. Screen refresh rate is also reported (`PlatformMacos.mm:305-345`).
- **Hidden/covered drawable handling:** Metal skips `nextDrawable` completely while the surface is hidden. It can acquire on a background thread for a <59 Hz screen, a >50 ms acquire, or repeated >=4 ms waits. If no drawable is ready it skips that displayed frame and continues GPU work; old-size drawables are discarded after resize (`MTLGfx.mm:457-475`, `MTLGfx.mm:552-604`, `MTLGfx.mm:618-636`, `MTLGfx.mm:645-648`). **Residual stall:** the first synchronous `nextDrawable` can still block before the >50 ms fallback is activated; no zero-wait guarantee follows from this code (`MTLGfx.mm:618-627`).
- **Vsync/pacing:** sessions force single core, emulation speed 1.0, vsync off, and smooth early presentation on. Metal uses the active vsync setting for display sync and avoids the normal `presentDrawable` route when automatic mode has vsync off (`Profile.cpp:75`, `Profile.cpp:180-189`, `Profile.cpp:241-248`, `MTLGfx.mm:30`, `MTLGfx.mm:655-676`).
- **Waiting notices:** during a session stall, overlay re-presentation skips hidden surfaces, limits refresh rate, and stops attempting it for that stall if a present takes over 50 ms (`Overlay.cpp:1382-1412`).

### B5. Orca overlay, chat, waiting notices, names, and menus

**The overlay does not require fullscreen.** It obtains the actual presenter picture rectangle, including letterbox/pillarbox offsets, and uses the visible intersection with the display. ### B6. Existing embedding support and what the host needs

**Yes: it already exists in 0.3.48 source.** Startup accepts `--embed --parent <decimal handle> --rect X Y W H` (or comma-separated rect), optionally `--embed-adopted`. Parent means HWND on Windows, CGWindowID on macOS, X11 window ID on X11. The parser requires a nonzero parent when embedding (`Embed.h:11-40`, `Embed.cpp:105-124`, `Embed.cpp:154-165`).

| Platform | Implemented mechanism |
| --- | --- |
| Windows | A `WS_CHILD` render window under the host, with sibling/child clipping and `SetWindowPos` rectangle updates. Adopted mode creates a hidden popup and waits for the launcher to make it a child before continuing (`PlatformWin32.cpp:123-158`, `PlatformWin32.cpp:179-202`, `PlatformWin32.cpp:321-334`). |
| macOS | A separate borderless, shadowless, non-key, mouse-transparent top-level window positioned above the host CGWindowID. It tracks host geometry/backing scale/Spaces and visibility; it is **not a cross-process NSView child**. Parent disappearance beyond a two-second grace stops Orca (`PlatformMacos.mm:111-126`, `PlatformMacos.mm:349-394`, `PlatformMacos.mm:475-490`, `PlatformMacos.mm:497-565`). |
| X11 | A borderless X window created under the parent with position/size updates and optional empty input shape; keys/mouse remain with the host. Parent destruction stops it (`PlatformX11.cpp:251-269`, `PlatformX11.cpp:350-359`, `PlatformX11.cpp:588-592`). Native Wayland cross-process embedding support is **UNKNOWN** from these platform implementations. |
